Get origin/PART-B-CL (one commit, 21fa0e0, about 2.3k lines: the period state machine, onboarding replay and control mining, restatement, execution, flux and the autopilot) ready to merge into main. That means: the local environment is reproducible, the branch obeys the binding accounting rules in .claude/rules/ and AGENTS.md, the debt the commit message admits to is paid down, and the hand-offs to workstreams A (gates), C (judgment and SoD) and D (surface) are clean. Problem

The branch is green: 61 tests pass, and the live year runs end to end in about 3 seconds against a scratch DB. But it isn't merge-ready, for these reasons (all verified in this session):

61 / 61tests pass on the branch
98.3% / 94.6%precision / recall at month 9

2 missedE-48, E-50: sales-lead self-approval
2 FPFN-0024, FN-0067: STALE-ACCRUAL
  1. Approvals with no approver. Hooks() defaults approve → "controller" and sign → "close_reviewer" (tpa/cycle.py, controller_approves / reviewer_signs_clean). Running the engine alone writes controller approvals and close sign-offs that no human made. That breaks rule 12 (traceable approvals) and the spec's line "it never approves anything".
  2. A change to A's gate file with no review. tpa/gates.py changes the stale-accrual gate (a disputed deduction now counts as arrived) and the window gate (allocated straddles are checked per share). AGENTS.md: "Don't weaken a gate to make a test pass." Neither change has a test proving the gate still blocks what it should.
  3. Thresholds tuned against the answer key. The commit says so. VARIANCE_NOISE_FLOOR_PCT, DRIFT_TOLERANCE_PCT and MATERIALITY_RATE are bare literals with no policy provenance (rule 6: thresholds come from company policy and are never presented as GAAP).
  4. Duplicated logic for program lookup, the activity-day split of straddling claims (onboarding.activity_share vs the allocate decision in execute.py) and the scan-back estimate (onboarding.estimate vs execute.scan_back_estimate). If replay and live disagree, the mined controls stop describing the live system.
  5. Never-cut items unmet on the B side. The SoD throw is a no-op (on_event = ignore_event), so E-48 and E-50 are missed. The autopilot resolves every finding without writing escalations or precedents, so the escalation-rate number, the spec's self-improvement proof, is flat at 0%.
  6. The environment isn't reproducible. .env is empty (0 bytes) and not in .gitignore. Nothing loads it. make db-up fails on this machine because the docker compose plugin is missing (colima is running Docker 29.x). The new spec.md, AGENTS.md, CLAUDE.md and .claude/rules/ are uncommitted on main.

Solution

Eight short phases. Each ends on make test plus make year plus the evaluator, run against a scratch DB, so every phase is commit-on-green. Order:

  1. Make the environment reproducible.
  2. Stop the engine approving anything on its own.
  3. Split out and prove the gate change, then get A's sign-off.
  4. Move every threshold into one company-policy module with provenance.
  5. Dedupe the replay and live math.
  6. Wire the minimal SoD throw and an escalation/precedent record, so E-48 and E-50 are caught and the escalation rate falls.
  7. Root-cause the two stale false positives.
  8. Rebase, verify the moment to the cent, and open the PR.

An optional ninth phase adds the period sign-off package and a CSV export ("verifiable through Excel"), which D needs.

Questionables

Should B implement can_approve and precedent writing, or wait for C?

Recommendation: B ships the minimal versions in Phase 6, since both are never-cut and E-48/E-50 plus the escalation-rate proof depend on them. The interfaces (can_approve(cur, actor, target_type, target_id), precedent key (control, conflict_type, customer)) follow the spec exactly, so C swaps in model-played humans without changing call sites. Confirm with C before Phase 6 so they don't build a parallel copy.

Are the two gates.py edits correct, or weakenings?

Assumption: correct. A disputed deduction is a claim that arrived (rule 03: an orphan accrual is one with no claims outstanding), and a straddling claim allocated by activity days should be window-checked per share. Phase 3 has to prove both with negative tests, and A has to approve. If A disagrees, revert the edit and make the engine satisfy the original gate.

If de-tuning thresholds lowers precision or recall, what then?

Report the lower number. The spec says to frame a mid-range number honestly, and rule 6 forbids passing tuned values off as anything else. A value the team chooses on purpose is fine if it is labelled as company policy with a rationale. A value fitted to the answer key isn't.

Mechanical auto-resolution by the agent (duplicates, no-proof, late returns): is that an "approval"?

Assumption: no. These post disputes or re-estimates only. That is holding or disputing, which rule 02 lets automation do, and it never clears or writes off.
